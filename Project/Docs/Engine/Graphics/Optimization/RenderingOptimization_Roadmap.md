# レンダリング最適化・軽量化ロードマップ

作成日: 2026-07-23
対象: CoreEngine レンダリングパイプライン全体

## 1. 目的

カメラ内にシーンの全オブジェクトが入った状態（近距離・全部見え）でも 60fps に貼り付かせる。
視錐台カリング・LOD・インスタンシングは「描く物の数と遠景の密度を減らす」施策であり、
**全オブジェクトが近距離で画面内にある状況では原理的に効かない**。この状況で効くのは以下の3系統。

1. 画面内でも実際には見えていない三角形を描かない（オクルージョン系）
2. 1三角形あたりのコストを下げる（ジオメトリ構造系）
3. 1ピクセルあたりのコストを下げる(解像度・シェーディング系)

## 2. 現状分析（2026-07-25 更新）

### 解決済み: 真因は「頂点統合されていない三角形スープ」だった

2026-07-23 時点でこの節には「主因は地形メッシュ `Terrain_Terrain_1` 等の巨大サブメッシュ」と
書かれていたが、**これは誤り**だった。2026-07-25 の調査で判明した事実:

- `Terrain_Terrain_1` は `Terrain.gltf` ではなく **島モデル `Small Tropical Island.obj` の
  サブメッシュ**（`o terrain`）。`Terrain.gltf` はシーン未使用でコード参照も 0 件。
- 島 1 体 239,058 三角形の内訳は 草 76,160 / 葉 71,526 / 植物 40,320 / **地形 32,768（14%）** /
  幹 12,460 / 岩 5,824。**地形は 14% しかなく、植生が 79%**。
- 真の原因は **Assimp のフラグに `aiProcess_JoinIdenticalVertices` が無く、
  頂点共有率ゼロの三角形スープをロードしていたこと**（実測 717,174 頂点 / 239,058 三角形
  ＝ちょうど 3.00 倍。OBJ 原本のユニーク位置は 256,205 個）。エンジン側の頂点溶接も不在。
- これが 2 つの問題を同時に起こしていた:
  1. post-transform vertex cache が完全に無効 → 頂点シェーダ実行回数が 3 倍以上
  2. `meshopt_simplify` が「同一位置の頂点が 3 個以上 → `Kind_Locked`」判定で全頂点を
     ロックし、エッジコラプス不能 → 全 LOD が誤差上限無効の `simplifySloppy`
     フォールバックで生成されていた（品質が悪いのに削減も中途半端）

### 修正の効果（2026-07-25 実測）

`ModelLoader::LoadAssimpFile` で `aiProcess_JoinIdenticalVertices` を有効化し、
`aiProcess_CalcTangentSpace` を統合後の独立パスへ移した（順序が重要。詳細は後述）。

| 指標 | 修正前 | 修正後 |
|---|---:|---:|
| 島モデル頂点数 | 717,174 | **269,245**（-62.5%） |
| ├ 地形サブメッシュ | 98,304 | **16,645**（5.9x） |
| └ 草サブメッシュ | 228,480 | **114,240**（2.0x） |
| G-Buffer GPU（4島全景） | 15.3〜15.7 ms | **5.5〜7.1 ms** |
| フレーム時間 | 25.5 ms | **16.8 ms** |
| FPS（4島全景） | 39 | **59.9（vsync 上限）** |

LOD も目標三角形数にぴったり着地するようになった（＝品質保証付きの `meshopt_simplify` が
通り、sloppy フォールバックが不要になった）。草 LOD2 は 1,410（崩壊）→ 4,569、
葉 LOD2 は 256（崩壊）→ 4,291。

**順序の落とし穴**: Assimp のポストプロセス実行順は `CalcTangentSpace` → `JoinVertices` に
固定されている。両方を `ReadFile` に同時指定すると、未共有状態で面ごとのタンジェントが
計算され「位置・法線・UV は同一だがタンジェントだけ違う頂点」が生まれて統合されない
（実測 717,174 → 698,627、2.6% しか減らない）。`CalcTangentSpace` は
`ApplyPostProcessing` で統合後に別パス適用すること。

## 3. 施策一覧と優先順位

### A. 三角形バウンドに直撃する施策（優先度: 高）

#### A-0. 頂点統合 ← **実装済み（2026-07-25）／最も効果が大きかった施策**
- 概要: ロード時に重複頂点を統合し、インデックス参照を共有させる。
- 効果: G-Buffer 15.5ms → 5.5〜7.1ms。詳細は 2 節。
- 教訓: **「三角形数バウンド」に見える症状の多くは実際には頂点バウンドである。**
  三角形を減らす A/B は頂点も比例して減らすため、両者を区別できない。
  新しいモデル形式を追加したときは `頂点数 / 三角形数` の比を必ずログで確認すること
  （0.5〜0.8 が正常、3.00 は完全非共有＝異常）。

#### A-1. Hi-Z オクルージョンカリング ← **実装済み**
- 概要: 深度バッファから階層深度ピラミッド（Hi-Z）を構築し、オブジェクト AABB を
  コンピュートシェーダーで遮蔽判定。遮蔽されたオブジェクトは次フレーム以降描画をスキップ。
- 効果: カメラ内でも手前の地形・建物の裏にある物を描かない。フラスタムカリングでは取れない削減。
  ただし島 4 体が横並びの現シーンでは相互遮蔽がほぼ無くカリング率 0.0%。
- 詳細設計: [HiZOcclusionCulling_Design.md](HiZOcclusionCulling_Design.md)

#### A-2. クアッドツリー / クリップマップ地形 ← **却下（2026-07-25）**
- 概要: ハイトマップ地形をタイル分割し、タイルごとに距離依存解像度で描画（CDLOD 方式）。
- **却下理由**: 前提となるハイトマップ地形が現シーンに存在しない。`Terrain.gltf` は
  シーン未使用・コード参照 0 件で、`Terrain_Terrain_1` は島 OBJ 内のサブメッシュだった。
  そのサブメッシュは島 1 体の 14%（32,768 三角形）しか占めず、仮に完璧に実装しても
  削減幅は 14% 止まりで 60fps には届かない。
- 再検討する条件: 手続き生成地形やハイトマップベースの広大な地形を導入する場合。

#### A-3. メッシュレット（クラスタ）カリング
- 概要: メッシュを 64〜128 三角形のクラスタに分割し、クラスタ単位で
  バックフェース・錐台・遮蔽カリング。`meshopt_buildMeshlets`（組み込み済みの meshoptimizer）で生成可能。
- 効果: 「1メッシュが巨大」なモデルをクラスタ単位で細かく落とせる。
  Mesh Shader（DX12 Ultimate）または ExecuteIndirect で実装。
- 備考: A-1 の Hi-Z ピラミッドをそのまま流用してクラスタ遮蔽判定に使える。

### B. ピクセル・解像度系の施策（優先度: 中）

#### B-1. 動的解像度スケーリング + アップスケール
- 概要: 内部レンダリング解像度を 70〜80% に落とし最終段でアップスケール
  （初期実装はバイリニア＋シャープン、将来 FSR2 系）。フレームタイム監視で自動調整。
- 効果: ライティング・水面・雲・ポストプロセスのコストが解像度比例で減少。
  「60fps 貼り付き」を仕組みとして保証できる最も汎用的な手段。三角形バウンド部分には効かない。

#### B-2. 可変レートシェーディング（VRS）
- 概要: 画面周辺部・低コントラスト領域を 2x2 レートでシェーディング。
- 効果: 中程度。B-1 の後で十分。

#### 注意: Z-prepass は非推奨
現状は三角形数バウンドのため、頂点を2回流す Z-prepass は逆効果になり得る。
ピクセルシェーダーバウンドに転じた場合のみ再検討。

### C. パス構成・時間方向の施策（優先度: 中）

#### C-1. 副次ビューの品質分離
反射ビュー・シャドウビューに、より強い LOD バイアス（+2）、短い描画距離カット、
オブジェクト種別フィルタ（小物は反射に描かない）を適用。

#### C-2. 静的シャドウのキャッシング
動かないオブジェクトのシャドウマップをキャッシュし、動的オブジェクトのみ毎フレーム上書き。
CSM 遠段カスケードの更新を 1/2〜1/4 フレームレートに間引き。

#### C-3. 重い画面系エフェクトのテンポラル分散
ボリューメトリック雲・ゴッドレイ・FFT 海面（3カスケード FFT 更新）を
半解像度＋テンポラル再構成、または隔フレーム更新化。

#### C-4. 非同期コンピュート
FFT・GPU パーティクル・LUT 生成をコンピュートキューへ移し、G-Buffer ラスタと並行実行。
三角形バウンドで固定機能が詰まっている間の ALU 空きを活用。

### 計測の原則（失敗から得た教訓）

1. **パスを最適化する前に、そのパスが本当にコストを持っているか GPU 実測で確認する。**
   2026-07-25 に従来型シャドウマップパスへカリング＋LOD を実装したが、Deferred 化で
   不透明モデルが `opaqueDrawQueue_` へ振り分けられており、そのパスは実測 0.001ms
   （クリアのみ）で完全な空振りだった。静的なコードリーディングだけで負荷源を
   判断してはいけない。
2. **「三角形数バウンド」と「頂点バウンド」を混同しない**（A-0 参照）。
3. 各施策の実施前後で、ビュー別 GPU 計測（`GpuTimestampProfiler`）と
   `EngineStats`（ドローコール・三角形数・頂点数）で効果を必ず計測すること。

### 未整理の残課題（性能とは別系統）

- テクスチャ圧縮の失敗警告が一部テクスチャで出ている
  （`TextureDdsCacheGenerator.cpp:53` の `Failed to compress texture`）。非圧縮 DDS で
  代替されるため VRAM と帯域を余分に食う。
- DDS キャッシュ生成は WIC 読み込みの副作用で走るため、**キャッシュ未生成の初回起動のみ
  非圧縮テクスチャが GPU に載る**（`TextureLoadExecutor.cpp`）。性能計測の交絡要因。
- 圧縮先が BC3 固定で用途を見ていない（`TextureDdsCacheGenerator.cpp:36`）。
  法線マップは BC5 が適切（性能ではなく品質の問題）。
